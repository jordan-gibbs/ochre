# Refinement baseline (synth-v1 eval)

Generated by `tools/eval/eval_refine.py` on 2026-10-04. Eval set: `training/refine/datasets/synth-v1/eval.jsonl` (100 examples, 20 per bucket A–E). Raw outputs: `tools/eval/out/refine-baseline-<system>.jsonl` (gitignored).

Every system runs the production prompt path: `prompts.system_prompt(ctx)` (mode, style, dictionary from each example; checked byte-identical to `crates/ochre-refine/src/prompts.rs` at start-up) and the `<dictation>` user message; local models get raw ChatML with the empty think block on llama-server `/completion`, greedy, with the `docs/refinement.md` §3.2 flags; output goes through `clean_output` + `normalize` (local) or `tidy` (cloud), then the guard (`refine/guard.py`, a line-for-line port of `guard.rs`). The Quill card-prompt row uses `You clean up dictated text.` plus the bare transcript.

## Per tag

Deterministic tag checks (n = examples carrying the tag):

- `self_correction`: no retracted word (in raw, not in clean, not a cue/function word) survives, no correction cue (no, wait, sorry, actually, I mean, scratch that, or rather, make that) appears more often than in clean, and no clean content word is dropped.
- `already_clean`: output is byte-identical to raw.
- `list`: same number of list lines and the same marker type (bullet vs numbered) as clean; no list when clean has none.
- `trailing_off`: ends with `...` and the last three words match clean (nothing invented); no `...` when the reference restarts.
- `voice_command`: same newline count as clean and the same count of spoken command words (`new line`, `period`, ...), so traps like "trial period" must keep the word.
- `discourse_filler`: each filler (like, you know, I mean, sort of, kind of, basically, literally, actually, so, okay so) appears as often as in clean.
- `question/request` (tags question, request_to_ai, command): not answered, and the same number of `?` as clean.

## Judge validation

Judge model: `gpt-4.1-mini` (temperature 0, JSON mode). Before the judge was trusted, its outputs were hand-checked against the GUIDE (`tools/eval/judge_validation.json`) and compared with its overall verdict. These cases go to the judge even when they are exact matches. **Agreement with the final rubric: 20/20** (the first 10 "tuning" cases: 10/10; the 10 "holdout" cases labelled afterwards: 10/10).

How the rubric got here. With the first rubric the judge agreed on 7/10 tuning cases; all three misses were false fails on optional commas or a misapplied R11. After the rubric spelled out which punctuation is optional, it agreed on 9/10. On 10 fresh holdout cases it then agreed on 8/10; both misses were false fails, one for digits vs spoken numbers and one for capitalising "God". The rubric now overrides both explicitly (guide rule 7 is moot because the normalizer runs afterwards). `gpt-5.4-mini` did no better on the same 20 cases (17/20) and cost about twice as much. Under R1 the judge also missed obvious acting (a written cover letter, a translated dictation), so it now answers a separate yes/no "acted" question, and a yes forces R1 to fail. Its remaining errors go both ways: it is too strict about commas in long run-on inputs, and it once accepted an unformatted dictated list. With the final rubric it agrees on all 20 cases, but those 20 cases shaped the rubric, so read the earlier 8/10 on fresh cases as the more honest estimate: the judge errs toward failing. The deterministic tag checks do not depend on the judge.

## Headline

- **Best local system: Quill 2B with the shared prompt.** Judge pass 58%, exact match 42%, WER 0.097, median latency 121 ms (p95 491 ms) on the RTX 5070 Ti.
- **Production default, Quill 0.8B with the shared prompt:** judge pass 40%, exact match 31%, WER 0.178, median 106 ms (p95 356 ms). It is safe (it acted on 2 of 100 dictations, and the guard caught both) but mostly passive. It returned the raw text unchanged on 17 of the 94 dictations that needed edits, applied 3 of 21 self-corrections, and formatted 0 of 4 dictated lists.
- **Cloud reference, gpt-4.1-nano:** judge pass 43%, exact match 34%, WER 0.140, median latency 550 ms. It is not a ceiling. It acted on 6 of 100 (it wrote a limerick, a cover letter, a D&D scene and an email reply; the guard caught all 6) and lowercased 9 of the 14 `casual` examples.
- **Quill's card prompt is unusable:** it acted on 36 of 100, the guard rejected 35%, and the judge passed 28%.
- **Bar for the fine-tune** (Qwen3.5-0.8B base): beat 2B on judge pass (58%), self-corrections (71% tag check) and acting (4%), at 0.8B latency (~106 ms median / ~356 ms p95 on GPU here).

Latency caveat: the GPU was shared. Another process held about 5 GB of VRAM throughout, but GPU utilisation was 0–2% before each run. Medians agree with `docs/refinement.md` §3.3 (0.8B, 41–100 words: 216 ms median; over 100 words: 356 ms), so contention probably moved the tails at most. Latency is measured in the primed steady state (the prefix for the example's own style is primed off the clock, as production does after each dictation). An app switch costs one unprimed request on top. By length (median ms): 0.8B 81 / 216 / 356, 2B 91 / 273 / 468, nano 503 / 648 / 981, for ≤12 / 41–100 / >100 words.

Spend: about $0.40 of OpenAI usage in total across all runs (cloud system, judge validation, two full judge passes).

## What the fine-tune must fix (ranked)

1. **Never act, including "translate", "respond to this email" and long prompts.** 2B acted on 4 of 100 and 0.8B on 2. The guard caught every case, so the user gets raw text with no cleanup at all. Translation requests and "respond/reply to this…" are the weak spots. A model that starts with a correct cleanup and then continues into an answer (D-0044) only fails `too_long` because the answer is long. Data: answer-bait at ≥ 20%, with translate, reply, write, role-play and "ignore previous instructions" variants, plus long multi-sentence prompts.
2. **Self-corrections, especially on 0.8B.** The tag check passes 3 of 21 on 0.8B (14%), 15 of 21 on 2B (71%) and 12 of 21 on nano (57%). 0.8B copies "no wait", "sorry", "actually" and "I mean" through verbatim. Even 2B misses corrections inside long text, restarts that repeat the clause, and terminal commands (`rm temp, scratch that, ls temp` became `rm temp, ls temp.`). This is the largest quality gap between the default model and the bar.
3. **Actually edit long, Parakeet-formatted input.** 0.8B returns 17 of 94 needed edits untouched. On dictations over 40 words the judge passes 3 of 27 for 0.8B and 12 of 27 for 2B. The failures are R6 (bad engine sentence breaks and commas kept, run-ons not split; the judge failed R6 on 36% of 0.8B outputs, versus 23% for 2B), stutters inside long text ("started returning, started returning"), and ignored dictionary spellings. The training mix needs plenty of 41–250-word Parakeet-style raw.
4. **False starts without a cue.** These fail silently: `B-0001` changed the meaning while passing the guard. `B-0045` ("I'm trying to learn, I'm trying to understand") and `B-0097` were kept. The judge passes 17% of false_start examples on both local models.
5. **Lists.** 0.8B formatted 0 of 4 dictated lists, 2B 2 of 4 (bullet point only, never "number one" or "first… second…"), and nano 0 of 4. The no-list traps were all handled, so list formatting is under-triggered rather than over-triggered.
6. **Keep meaningful words: precision on fillers.** Both local models remove deliberate repetition (2 of 2). 2B drops meaningful "actually", the casual "Okay so" opener and "Nah", and keeps the meaningless "basically" (discourse_filler tag check: 2B 40%, 0.8B 60%). The guard rejects drops like "Nah", so the user gets raw text.
7. **Small format rules.** Every system missed trailing-off `...` (0 of 2). Both local models appended a period to all 4 terminal commands in `literal` context, against the style hint. Spoken "question mark" was kept as words once (`E-0038`) and the final "new line" was missed in `E-0039`. Already-clean input came back identical 4 of 6 times on both local models.
8. **Hold latency.** This is a constraint, not a bug: stay on the 0.8B base with output length close to the input (~106 ms median / 356 ms p95 on this GPU, under load).

**Fix before generating training data (prompt and label mismatches, not model bugs):**

- The production system prompt says *"Write numbers, times, dates, emails and URLs the way people type them"*, while GUIDE rule 7 (and the normalize-after-model design) keeps them as spoken words. The models obeyed the prompt in 3–10% of examples (nano 10%). Training targets rendered with this prompt would contradict it. Either drop that rule from the prompt for the verbatim tier, or write the targets in written form with `"normalized": true`. The harness neutralises this by passing both sides through `normalize()` and telling the judge that digits are equivalent, but `normalize()` does not cover ordinals ("thirteenth" vs "13th"), "four oh one" or "Pixel seven".
- The `casual` style hint allows lowercase starts and dropping the final period, but no `casual` reference in synth-v1 does either (0 of 14). Nano took the hint 9 of 14 times. Decide which one is right and align the GUIDE or the hint.

**Eval-set caveats.** There are 100 synthetic examples, and some tags are tiny: trailing_off n=2, voice_command n=5, already_clean n=6, list n=7 (4 real lists). Treat per-tag percentages as ±20–40 points. The judge errs toward failing (see the validation above), so judge pass rates are slightly pessimistic for every system alike. The deterministic checks also undercount some failures: a correction whose retracted words reappear in the corrected text is only caught by the cue check.
